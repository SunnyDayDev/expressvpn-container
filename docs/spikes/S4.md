# S4 — достижимость SOCKS5 на `127.0.0.1` Mac'а из контейнера и UDP

Дата: 2026-08-25. Среда: Docker Desktop / Apple Silicon; вместо реального xray —
тестовый двойник (sing-box socks-inbound в контейнере, опубликован на
`127.0.0.1:1086` Mac'а). Проверка с реальным xray пользователя — отдельным шагом
(см. «Что осталось»).

## TCP: работает

- `host.docker.internal` резолвится в `192.168.65.254` (IPv4; есть и IPv6-запись —
  в контейнере IPv6 отключён, поэтому резолвить нужно `ip4`, агент так и делает).
- Слушатель, привязанный к `127.0.0.1` Mac'а, достижим из контейнера через
  `host.docker.internal:<port>` — проверено и голым слушателем, и тестовым
  SOCKS5: TCP CONNECT через прокси из контейнера работает.
- Полный путь socks5-uplink подтверждён: `xup0` (sing-box TUN) → socks-outbound
  (bind eth0) → `host.docker.internal:1086` → интернет. Домены резолвятся через
  DoH-over-proxy (перехват порта 53), `tcpdump -i eth0 udp port 53` — 0 пакетов.

## UDP: механика работает, но в сети пользователя UDP/53 наружу блокируется

- UDP ASSOCIATE через тестовый прокси проходит, датаграмма доходит до прокси и
  пересылается в цель (видно в логах прокси).
- Ответ от `1.1.1.1:53`/`8.8.8.8:53` **не возвращается вовсе** — прямой UDP/53
  к публичным резолверам блокируется в текущей сети (проверено `dig` из
  контейнера мимо всякого прокси: timeout). Это свойство сети/региона, не бага.
- Следствие: probe (UDP ASSOCIATE + DNS-датаграмма к 1.1.1.1, таймаут 3 с)
  корректно даёт `udpSupported=false`, и ExpressVPN пойдёт по `lightway_tcp` —
  ровно для этого сценария и проектировался `protocol.effective` (D6).
- BND.ADDR relay: `0.0.0.0`/loopback заменяется адресом прокси (так ведут себя
  xray/dante); нестандартный «чужой» IP в BND.ADDR не чиним — это артефакт
  тестового двойника в другой docker-сети.

## Настройки xray (для реального инстанса пользователя)

- socks-inbound: `"udp": true` — иначе UDP ASSOCIATE будет отклонён;
- `listen: "127.0.0.1"` на Mac'е достаточно (host.docker.internal достаёт);
  на Linux/NAS `host.docker.internal` нет — xray указывается по IP docker-шлюза
  или общей docker-сети (см. README/deployment).

## Проверка на реальном xray (2026-08-25)

Тестовый инстанс xray жил не на loopback Mac'а, а на роутере в LAN
(`<router-ip>:<port>`).

- Из контейнера достижим напрямую по IP, `host.docker.internal` не нужен.
- TCP: полный стек работает — VPN подключается через
  `tun0 → xup0 → sing-box → xray`, стабильный Connected, выход ExpressVPN.
- UDP: probe нестабилен (то ассоциация проходит с ответом, то «UDP ASSOCIATE
  rejected») — фактически `udp` у этого xray не включён/ненадёжен;
  `udpSupported=false` → `lightway_tcp`. При включении `"udp": true` в
  socks-inbound probe подхватит UDP автоматически (`probe-uplink` или
  переприменение конфига).
- Рекомендация для маломощных роутеров: `uplink.socks5.udp: "off"` даёт
  детерминированный TCP и минимальную нагрузку.
