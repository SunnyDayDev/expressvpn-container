# S2 — маршруты/фаервол демона 14.x и совместимость с uplink-TUN

Дата: 2026-08-25. Статус: **завершён** (реальный вход и подключения выполнены
в обоих режимах uplink'а, включая реальный xray).

## Главные выводы (проверено подключениями)

1. **Демон корректно стыкуется с uplink-TUN**, но default-маршрут обязан быть
   `via <gateway-ip>`: Lightway ищет именно IP шлюза и на device-route без via
   падает мгновенно с «Failed to find default gateway: No such process» →
   бесконечный цикл переподключений. Агент ставит
   `default via 172.29.0.2 dev xup0` (peer TUN) — после этого демон ставит
   `<vpn-server>/32 via 172.29.0.2 dev xup0` и туннель строится через прокси
   (проверено: маршрут к серверу ExpressVPN идёт через xup0, стабильный Connected).
2. **Маршруты демона при connect (host-режим)**: `0.0.0.0/1` и `128.0.0.0/1`
   via `<tun-gw>` dev tun0; `<vpn-server>/32` — через прежний default.
   Также policy-роутинг: `50: from all lookup main suppress_prefixlength 1`,
   `70: fwmark 0x3214 lookup evpnFwdrt` (+blackhole) — с нашей схемой не
   конфликтует.
3. **resolv.conf при connect** демон переписывает на **DNS туннеля**
   (`nameserver 100.64.100.1`, маршрут к нему — только через tun0), при
   disconnect восстанавливает прежний. Это источник remote DNS для прокси
   (контур 2 из D5): резолвер читает resolv.conf на каждый запрос.
4. **Метка 0x5050 не перезаписывается** и при подключённом демоне (клиентский
   трафик прокси ходит через tun0; проверено сквозными curl'ами).
5. **DNS-защита демона**: при подключении он анкерит `blockDNS`
   (REJECT udp/tcp 53 в OUTPUT, кроме своего резолвера). Следствия:
   датаграммы UDP-relay к произвольным DNS-серверам получают EPERM — это
   штатная защита ExpressVPN от DNS-утечек, а не бага; DNS через relay
   работает к туннельному резолверу, не-DNS UDP не ограничен.
6. **Фаервол демона «enabled when connected» реален**: `set networklock false`
   выключает лишь постоянный режим; при подключении демон всё равно анкерит
   `blockAll`/`allowVPN` и режет весь не-туннельный egress (проверено:
   eth0-bound curl при host+connected → rc=7). Нашему kill switch это не
   мешает (двойная защита); но «IP uplink'а» в host-режиме при подключённом
   VPN изнутри не измерить — self-check пропускает этот замер. В socks5-режиме
   путь eth0→прокси остаётся разрешённым, замер работает.

## Что демон 14.x делает с сетью уже на старте

- Ставит большой набор цепочек `evpn.*` через iptables-nft во всех таблицах
  (filter/nat/mangle/raw, IPv4+IPv6). Все «фичи»-цепочки (`blockAll`, `blockDNS`,
  `vpnTunOnly`, …) существуют, но **не активированы**: якорные цепочки `evpn.a.*`
  пусты, пока Network Lock выключен и VPN отключён.
- fwmark'и демона: `0x3211` (bypass-приложения, cgroup 1383), `0x3212`
  (vpn-only, cgroup 1384), `0x3213` (wireguard), `0x3214` (tagFwd).
- `ip rule`: `from all fwmark 0x3214 lookup evpnFwdrt` (priority 70) — policy
  routing для *форвардящегося* трафика.
- Группы: демон метит собственный трафик через `skgid 1000` (группа
  `expressvpn`) — правило `evpn.r.400.allowSelf: skgid 1000 accept`.

## Вывод для kill switch (D4): метка 0x5050 живёт

- Безусловный `MARK set 0x3214` стоит **только в mangle PREROUTING** (tagFwd) —
  он не касается локально порождённых пакетов нашего прокси.
- В mangle **OUTPUT** демон метит только по cgroup (split tunnel — выключен) и
  по subnet-правилам (не настроены). Перезаписи `SO_MARK=0x5050` наших сокетов
  нет → **mark-вариант kill switch выбран**, uid/gid-вариант остаётся запасным.
- Значения 0x3211–0x3214 с 0x5050 не пересекаются.

## Uplink поверх xup0 (без демона connect — но с реальным трафиком)

Проверено на тестовом SOCKS5 (см. S4): агент ставит маршруты по D3
(`default dev xup0`; `<proxy>/32 via 172.18.0.1`; запасной default metric 1000),
sing-box с `auto_route: false` не создаёт ip rules, весь трафик контейнера
(включая демонский до connect: его API-запросы) уходит в xup0 → прокси.
resolv.conf на время socks5-режима переключается на перехват sing-box
(`nameserver 172.29.0.2` → hijack-dns → DoH через прокси); `tcpdump udp port 53`
на eth0 пуст. Демон, стартовавший в socks5-режиме, скачивает свои JSON-конфиги
через прокси (видно в daemon.log: `200 OK`).

## resolv.conf и DNS демона

- Docker (compose-сеть) даёт `nameserver 127.0.0.11` (embedded DNS). Демон до
  подключения его не переписывает.
- В составе клиента есть `expressvpn-unbound` — локальный резолвер; как демон
  правит resolv.conf **при connect** — снять после логина (см. ниже).

## Эксплуатационные заметки

- CLI `connect` возвращает rc=0 **до** установления туннеля — агент сам ждёт
  `get connectionstate == Connected` (иначе ложные успехи и гонки супервизора).
- При неудачах подключения агент явно выполняет `disconnect` между своими
  пейсированными попытками — собственный реконнект-цикл демона иначе молотит
  uplink (в socks5-режиме — пользовательский прокси/роутер) без пауз.
- Наблюдался инцидент: реконнект-шторм через xray на домашнем роутере совпал с
  деградацией всей LAN; после пейсинга и фикса default-gateway шторм исключён.
