# Design: optional-admin-password

## Context

Мотивация — в proposal.md. Текущее устройство:

- «Пароль задан» = наличие файла `<dataDir>/auth/password` (`SessionManager.HasPassword`, `internal/api/sessions.go`). Отсутствие файла неотличимо от свежего тома, поэтому UI в этом случае всегда требует создать пароль.
- `authorized()` (`internal/api/server.go`) принимает Bearer-токен или cookie-сессию; CSRF — double submit cookie для мутирующих методов.
- CLI `detour-agent reset-password` (запускается с хоста отдельным процессом) удаляет файл пароля; работающий агент замечает смену «версии» файла (mtime+size) и сбрасывает сессии.
- UI: `App.svelte` выбирает фазу по `GET /v1/auth/status` (`passwordSet`/`authenticated`); онбординг — `Setup.svelte` (шаг 1 — пароль); Access — смена пароля, logout-all, API-токен.
- Дизайн-макеты уже обновлены: `design/expressvpn-sidecar-design.pen`, артборды 10b (skippable setup), 5b (Turn off…), 5c (Access при выключенной защите).

## Goals / Non-Goals

**Goals:**
- Третье персистентное состояние защиты (`disabled`), переживающее рестарт контейнера и различимое со свежим томом.
- Все переходы — «живые», из UI, без пересоздания контейнера (в духе принципа «никаких recreate-параметров в этом API»).
- Не ослаблять защиту от cross-site запросов из браузера пользователя при выключенном пароле.
- Существующие развёртывания с паролем не замечают изменений.

**Non-Goals:**
- Выключение защиты через env-переменную/compose (стало бы recreate-параметром — противоречит принципу честности UI).
- Изменение аутентификации входящего SOCKS5-прокси (`proxy.auth`) — отдельный механизм, не трогаем.
- Роли, несколько пользователей, ограничение по IP.

## Decisions

**1. Персистентность `disabled`: маркер-файл `<dataDir>/auth/disabled` рядом с файлом пароля.**
Состояние выводится из пары файлов: только `password` → `set`; только `disabled` → `disabled`; ни одного → `unset` (оба сразу — некорректно; `password` побеждает, маркер удаляется). Альтернатива — ключ в `config.json` — отвергнута: конфиг декларативный и редактируется через `PATCH /v1/config`, а смена режима защиты должна проходить только через auth-эндпоинты со своими проверками (подтверждение паролем). Механика «версии файла пароля» для инвалидации сессий не меняется.

**2. API: отдельные `POST /v1/auth/skip` и `POST /v1/auth/disable`, расширенный `/v1/auth/status`.**
`skip` — публичный, но только в состоянии `unset` (как сегодня `setup`); `disable` — требует тела с текущим паролем и работает под общим троттлингом с `login` (иначе он становится обходом троттлинга для перебора). `setup` остаётся «создать пароль, пока он не задан» и в состоянии `disabled` дополнительно удаляет маркер. Альтернатива — флаг `{"skip": true}` в `setup` — отвергнута: у пропуска и создания разные предусловия и разная семантика ошибок. В `status` добавляется `authDisabled`; при выключенной защите `authenticated: true` (UI ничего не должен спрашивать).

**3. Обход аутентификации — в `authorized()`, плюс Origin-щит для мутаций.**
При `disabled` `authorized()` возвращает true. Но cookie+CSRF защищали не только от чужих в сети — они защищали от чужих *страниц в браузере владельца*: `fetch` в режиме no-cors может слать POST/PATCH с JSON-телом на `http://nas.local:48100` с любого сайта (Content-Type не проверяется), а худший сценарий — перевод `uplink.socks5.host` на сервер атакующего, т.е. перехват всего VPN-трафика. Поэтому при `disabled` мутирующие запросы (не GET/HEAD/OPTIONS) отклоняются с `403`, если `Origin` присутствует и не совпадает с origin запроса (Host), либо `Sec-Fetch-Site: cross-site`. Запросы без этих заголовков (curl, скрипты, SPA с same-origin) проходят. Альтернатива — оставить всё открытым — отвергнута как реальный вектор перехвата трафика; альтернатива — требовать токен для мутаций — отвергнута: это «пароль под другим именем», ломает смысл фичи.

**4. Bearer-токен при `disabled` не требуется, но эндпоинты токена продолжают работать.**
Скрипты с токеном не ломаются при включении/выключении защиты. UI подписывает у токена «не требуется, пока защита выключена».

**5. UI: фаза выбирается по `authDisabled`, Access — по состоянию.**
`App.svelte`: `authDisabled → app` (минуя login/setup); «Sign out» в сайдбаре скрыт. `Setup.svelte`: на шаге 1 — ссылка «Continue without password» + предупреждение; после `skip` онбординг продолжает шаг 2 (макет 10b). `Access.svelte`: при `set` — «Change…» и «Turn off…» (подтверждение текущим паролем, макет 5b); при `disabled` — warn-баннер, форма «Set password…», без строки Sessions (макет 5c). После «Set password» агент выдаёт cookie-сессию сразу (как в `setup` сегодня), чтобы текущая вкладка не попала на login.

**6. `reset-password` CLI остаётся «вернуть в `unset`»: удаляет и файл пароля, и маркер.**
Это аварийный вход при забытом пароле; после него UI снова предлагает setup (с возможностью пропустить). Отдельная CLI-команда «disable» не нужна — выключение доступно из UI.

## Risks / Trade-offs

- [Пользователь выключает пароль в общей/офисной сети, не осознав последствий] → предупреждение в двух местах (шаг онбординга и Access-баннер), выключение существующего пароля — только с подтверждением текущим паролем.
- [Origin-проверка сломает нестандартный reverse-proxy, переписывающий Host, но сохраняющий Origin браузера (например, DSM-прокси `expressvpn.home`)] → сравнивать Origin с заголовком `Host` запроса (после прокси они совпадают у same-origin запросов); `Sec-Fetch-Site: same-origin`/`same-site`/`none` принимаются; в диагностике — понятная ошибка `403 cross_site_blocked`.
- [DNS rebinding: атакующий сайт резолвит своё имя в адрес NAS; тогда и `Origin`, и `Host` несут имя атакующего и совпадают — Origin-щит и `Sec-Fetch-Site: same-origin` это не ловят] → остаточный риск принят: он существует только при сознательно выключенной защите и требует целевой атаки; полноценная защита (allowlist хостов) — вне рамок. При включённом пароле rebinding не работает (cookie привязана к хосту).
- [Гонка `skip` с двух вкладок или `skip` после того, как другая вкладка создала пароль] → предусловия проверяются атомарно по файлам; `skip` при `set` → `409`, UI перечитывает `status`.
- [Маркер и файл пароля существуют одновременно после сбоя] → детерминированное разрешение: `password` побеждает, маркер тихо удаляется при старте/проверке.

## Migration Plan

Изменение аддитивно: новые эндпоинты и поле `authDisabled`; поведение при существующем пароле не меняется. Откат — обычный откат образа: маркер `auth/disabled` старый агент игнорирует (файл неизвестен), защита снова станет обязательной, UI предложит login/setup как раньше.
